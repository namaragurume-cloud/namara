# 検索・推薦ロジック（SEARCH_RANKING）

実装：`src/lib/search/parser.ts`（解析）、`src/lib/search/ranking.ts`（推薦）、`src/lib/ads/selector.ts`（広告）

## 1. 役割分担
- **AI（将来は OpenAI）＝条件の抽出だけ。** 店舗の選定・価格・営業時間には関与させない。
- **推薦エンジン＝構造化データでの絞り込みと順位付け。** 同じ入力なら必ず同じ結果（テストで確認）。

## 2. 解析（parser.ts）
1. 全角→半角などの表記ゆれをそろえる（NFKC）
2. 予算：「8000円」「1500円以内」「3000〜5000円」「1万円くらい」「五千円まで」→ 1人あたりの上限・下限・目安
3. 人数：「4人」「ふたり」 / 日時：「明日」「19時」（参考情報。空席確認はしない）
4. 時間帯：「ランチ」→昼、「ディナー・夜・飲み」→夜（「夜景」「深夜」は除外）
5. 辞書照合（長い語から）：エリア・市・ジャンル・利用シーン・希望条件
6. 残りの語を「その他キーワード」に（ひらがなだけの語・定型語は除外）
7. `normalizeConditions()` で重複除去・矛盾解消（OpenAI の出力もここを通す）

## 3. 推薦（ranking.ts）

### 必須条件（1つでも満たさない店は表示しない）
- 公開済み かつ 運営の検証済み
- エリア（指定時）／市（「札幌」など）
- ジャンル（指定時、店舗のいずれかのジャンルが一致）
- 希望条件（個室・禁煙・子連れOK など。すべて満たす）
- ランチ指定時：ランチ営業の価格情報がある
- 予算指定時：価格情報が確認でき、予算内に収まるメニューがある
  - 「以内」：店の最低価格 ≤ 上限
  - 「〜円くらい」：最低価格 ≤ 目安×1.2
  - 「以上」：最高価格 ≥ 下限
  - 価格不明の店は予算付き検索に出さない

### 加点（順位の理由として記録・表示）
| 理由 | 点 |
| --- | --- |
| メインジャンルが一致 | 30（サブジャンル一致は 20） |
| エリア一致 | 20（市レベル一致は 10） |
| 予算内に収まる | 20（上限を超えるメニューもある場合 8） |
| 利用シーン一致 | 10（最大2つ） |
| 希望条件一致 | 各5 |
| キーワード（店の特徴タグ）一致 | 各8 |
| 情報確認から90日以内 | +5 |
| 情報確認から180日超 | −10（注意書きも表示） |

同点は「情報確認日が新しい順」→ 店舗ID順。

### その他
- 条件が何も読み取れないときは推薦しない（案内文を返す）。
- エリア等が無く「デート」などシーンだけの検索では、シーンかキーワードが一致した店だけを出す。
- 5件未満でも条件を緩めて埋めない。代わりに「〇〇を外すと N 件」の提案を表示。

## 4. 広告枠（selector.ts）
通常の5件を決めた **後で**、別枠として最大1件を選ぶ。通常順位は一切変わらない（テストで確認）。
詳細は [AD_POLICY.md](AD_POLICY.md)。

## 5. 計測
`search_submitted / search_parsed / recommendation_shown / store_detail_clicked / map_clicked / reservation_link_clicked / store_saved / search_refined / no_result`
- 表示・クリックはサーバー側で記録（クライアントから送れるのは「保存」のみ）
- クリックは「その検索で実際に表示した店」のみ・同じ検索×店×種類は1回まで

## 6. 今後の改善（Phase 3 後半〜）
- OpenAI で言い換え・口語表現の解析精度を上げる（出力は Zod で検証、失敗時は辞書解析にフォールバック）
- 「近く」「駅から徒歩5分」など距離条件（位置情報の同意が必要）
- クリック率を使った順位学習は、表示位置の偏りを補正できるデータ量になってから検討
